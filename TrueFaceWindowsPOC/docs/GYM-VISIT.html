Gym visit checklist — TrueFace door test

Print this page and keep it next to the Windows laptop during the visit. Follow the steps in order. Tick each box as you finish it.

We do not use the gym website or gym database We talk only to the door tablet Never change a real member

1. Why we are doing this

What: A short live test on the real TrueFace door tablet to prove the software can create a temporary test person, turn their access off and on, and remove them cleanly.

Why: The final gym product will use this same tablet connection. If this visit works, we know door allow/deny can be controlled from our software. If it fails, the website cannot fix it later — we need to know now.

What this does not prove: The gym website, online login, cloud connection, or member payments. Those are separate visits.

Important idea: We only create one throwaway person whose id looks like POC-20260912-A3F2. We never edit, freeze, or delete a real gym member on the tablet.

2. Before anyone arrives (gym staff)

Do these on a calm day before the visit starts.

A. Close other tablet software

What: Fully quit Interactive Attendance (IAS) and any other program that talks to this tablet.

Where: On the PC or laptop that normally runs IAS for this door.

How: Exit the program completely (not just minimize). Confirm it is not still running in the system tray.

When: Before we plug in our laptop and start the test.

Why: Only one program may talk to the tablet at a time. If two programs connect, the tablet can kick one off or behave strangely.

B. Backup the people already on the tablet (strongly recommended)

What: Export / backup the current user list from IAS or from the tablet’s own menu.

Where: IAS backup/export screen, or the tablet admin menu (whichever your gym already uses).

How: Use the same backup steps you already know for this tablet. Keep the file somewhere safe.

When: Before the test begins.

Why: Faces stay only on the tablet — our tool cannot copy them. Our cleanup only removes the temporary POC-… person we add. A backup is extra safety if something unexpected happens.

C. Write down tablet connection details

What: Have ready:

  • Tablet LAN IP address (example: 192.168.1.50)
  • Port 37777 (usually this number; do not change it unless your installer says otherwise)
  • Tablet admin username and password (the login used on the device itself)

Where: From the person who set up the tablet — not the gym website login.

Why: Our laptop must log into the tablet on the local Wi‑Fi/LAN like a technician tool.

D. Arrange a test person

What: One volunteer who can stand in front of the door camera twice (once when access should work, once when it should not, then again when it should work).

When: Available for about 15–30 minutes during the visit.

Why: We must prove the physical door responds, not only that the laptop screen says “OK”.

You do not need: the gym website running, MySQL, cloud firewall changes, or production API access. The laptop only needs to reach the tablet on the same local network.

3. Set up the Windows laptop (operator)

E. Put the software on the laptop

What: Copy the project folder that contains both TrueFaceWindowsPOC and gateway onto the Windows PC.

Where: Any easy path, for example C:\gym\.

How: USB drive, zip, or git clone — whatever you used to bring the files.

Why: The test program needs both folders; it reuses the same tablet code the real gateway will use.

F. Install .NET (if not already installed)

What: Install the .NET SDK that can run this project (net10.0).

Where: On the Windows laptop.

How: Install from Microsoft’s .NET download page, then open a new Command Prompt and type dotnet --version to confirm it works.

When: Before the first run.

G. Connect to the same network as the tablet

What: Join the gym LAN / Wi‑Fi that can reach the tablet IP.

How to check: From Command Prompt: ping 192.168.x.x (use the real tablet IP). You should get replies.

Why: If ping fails, the test cannot log in. Fix network first; do not continue.

H. Prepare a small face photo (optional but useful)

What: One JPEG photo of a face for the “remote upload” probe.

Where: Save it on the laptop, e.g. C:\gym\test-face.jpg.

Why: We expect the tablet to reject remote photo upload. We still need to try once and write the error into the log. Door success later uses face enrollment on the tablet screen, not this photo.

If you have no photo, you may run with --skip-face-upload (see command below). Door tests can still run after on-tablet enroll.

I. Start the test program

Where: Open Command Prompt (or PowerShell).

How:

  1. Go into the POC folder: 
    cd C:\gym\TrueFaceWindowsPOC
    (Use your real path.)
  2. Set the tablet details (replace with real values; do not share the password in chat or email later): 
    set TRUEFACE_IP=192.168.1.50
set TRUEFACE_USERNAME=admin
set TRUEFACE_PASSWORD=your-tablet-password-here
  3. Start the full visit (with face photo probe): 
    dotnet run -- --face-image C:\gym\test-face.jpg

Other useful starts:

  • No door walks (only login + create/delete) — use only if you cannot test the door today: 
    dotnet run -- --skip-door --skip-face-upload
    If you use --skip-door, you must not claim allow/deny worked.
  • No photo probe, but still do door walks: 
    dotnet run -- --skip-face-upload

What you will see: Lines print on screen and also save to a file named like poc-run-20260912-143022.log in the same folder. Keep that file.

Safety: Never put the tablet password into the log by typing it into chat. Prefer the set TRUEFACE_PASSWORD=... method. Do not commit passwords or face photos to git.

4. Live test steps (follow the laptop prompts)

The program pauses and asks you to press Enter at key moments. Read the on-screen message, do the physical action, then press Enter. If something goes wrong, press Ctrl+C once — the program will try to delete the temporary person.

Do not do any of these during the test
  • Do not factory-reset the tablet.
  • Do not reboot the tablet “to fix it.”
  • Do not change the tablet’s clock.
  • Do not use “remote open door” from any app as the allow/deny proof — that opens the door without checking membership.
  • Do not create, edit, freeze, or delete any user except the one whose id starts with POC-.
  • Do not start IAS again until this test has fully finished and exited.

Step 1 — Laptop logs into the tablet

What happens: The program connects using the IP and admin password you set.

Where to look: On the laptop console / log.

Pass looks like: Connected / online, a serial number, and a channel count. No login error.

Fail looks like: Login error with a code and message. Stop. Check: IAS closed? Correct IP? Correct password? Same network?

Why: If login fails, nothing else can be trusted.

  • Login succeeded

Step 2 — Take a “before” photo of who is on the tablet (user list)

What happens: The program lists every person id already on the tablet (names and frozen/not frozen if available). No faces are copied.

Where to look: Laptop log shows a count and a sorted list of ids.

Pass: List prints without an error.

Fail: “Find user” / list failed — stop; we cannot safely clean up without a before-list.

Why: At the end we compare this list to the final list. They must match exactly (except we briefly add then remove our POC-… person).

  • Before-list printed

Step 3 — Create the temporary test person

What happens: The program creates one new person with an id like POC-20260912-A3F2 and a clear test name (for example “POC Test”).

Where: Only on the tablet, through our laptop program — not on the gym website.

Pass: Create succeeds, and that id appears when the program lists people again.

Fail: Create error codes in the log. Stop if create failed; there should be nothing to clean up. If create partly succeeded, keep the id from the log for cleanup.

Why: We must never risk a real member’s record. A tagged POC-… id is easy to find and delete.

Write it down: POC id = _______________________________

  • POC person created and visible

Step 4 — Rename / adjust the temporary person

What happens: The program changes the display name (for example to “POC Renamed”) and validity dates.

Pass: Re-list shows the new name.

Fail: Update failed in the log.

Why: Proves we can change a person the same way the real product will.

  • Rename visible on re-list

Step 5 — Try sending a face photo from the laptop (expected to fail)

What happens: If you gave --face-image, the program tries to upload that JPEG to the tablet for the POC person.

Where: Automatic on the laptop — you do not tap the tablet for this step.

Pass for this visit: The attempt is logged with a result and an error code. Often the code is 0x10030110. The program must not say remote enroll “succeeded.” The photo bytes are never printed in the log.

Fail (serious): The program crashes. Stop the visit carefully; still try cleanup (Ctrl+C or let it finish cleanup). Note what happened.

Why: We already expect remote photo enroll to fail on this firmware. The log is evidence. Real face capture for the door test is the next step, on the tablet itself.

If you used --skip-face-upload, tick “skipped” instead.

  • Face upload probe logged (or intentionally skipped)
  • We did not treat remote upload as product success

Step 6 — Enroll the face on the tablet screen (required for door walks)

What: Teach the tablet the test person’s face using the tablet’s own menus.

Where: On the TrueFace tablet touch screen (device admin / user / face enroll screens — use the same path your installer uses for adding a face to a person).

How:

  1. Find the person whose id is the POC-… id you wrote down (name may show as “POC Renamed”).
  2. Enroll / capture face for that person only.
  3. Do not enroll under a real member id.
  4. When the tablet says enroll is done, go back to the laptop.
  5. When the laptop says to press Enter after enroll — press Enter.

When: After create/rename (and after the photo probe if you ran it), before the first door walk.

Why: The door camera needs a face stored on the device. Laptop photo upload is not trusted for this.

If the gym refuses on-device enroll, skip door walks (--skip-door next time) and do not claim allow/deny.

  • Face enrolled on tablet for POC id only; Enter pressed on laptop

Step 7 — First door walk (should ALLOW)

What: Prove the temporary person can open / be granted access.

Where: At the physical door / tablet camera. Watch the laptop for the event line.

How:

  1. Read the laptop message, then press Enter when it asks you to start the walk.
  2. Have the test person stand in front of the tablet like a normal entry.
  3. Wait for the laptop log to show an ACCESS event for the POC-… id with access granted (look for wording like granted=true or “Grant event”).

Pass: Event for the correct POC id, granted yes, within the wait time (default about 90 seconds).

Fail: Timeout, wrong person id, or no event. Note it; cleanup still matters later.

Why: Baseline: access works while the person is enabled.

  • First allow walk confirmed in the log

Step 8 — Turn the temporary person OFF (disable / freeze)

What: The laptop tells the tablet to freeze / disable the POC person (they stay on the list but should not get in).

Where: Automatic from the laptop program — you should not manually freeze other people on the tablet.

Pass: Disable succeeds; re-list may show them as frozen.

Fail: Disable error in the log.

Why: This is how expired or unpaid memberships will be blocked in the real product.

  • Disable succeeded

Step 9 — Second door walk (should DENY)

What: Prove a disabled person cannot get in.

How:

  1. Press Enter on the laptop when asked.
  2. Same test person tries the door again.
  3. Watch for either:
    • Laptop log shows ACCESS for the POC id with granted false, or
    • Door clearly stays locked / denied — when the laptop asks, type YES (door stayed locked) or NO.

Pass: Deny event in the log, or operator typed YES and that answer is written into the log.

Unclear: If you are not sure, the log may say UNVERIFIED — still continue to re-enable and clean up.

Why: Without this, we cannot trust “membership off” at the door.

  • Deny proven (event or YES in log)

Step 10 — Turn the temporary person ON again (enable)

What: Laptop unfreezes the POC person.

Pass: Enable succeeds in the log.

Why: Membership can be restored without deleting the person.

  • Enable succeeded

Step 11 — Third door walk (should ALLOW again)

What: Same as step 7 after re-enable.

How: Press Enter when asked; test person walks; laptop shows grant for the POC id again.

Pass: Second grant / allow event in the log.

Why: Proves disable was reversible — not a broken user.

  • Second allow walk confirmed

Step 12 — Delete the temporary person and compare lists

What: Laptop deletes only the POC-… person, then lists everyone again.

Pass:

  • POC id is gone.
  • The set of remaining ids matches the before-list from Step 2 exactly.
  • Log contains a clear line like POC PASS.

Fail: POC still present, or any other id appeared/disappeared → POC FAIL even if earlier door walks looked good. Follow section 5 below.

Why: Leaving a test person on a live door tablet is not acceptable.

  • Delete succeeded
  • Before and after user lists match
  • Log says POC PASS

5. If cleanup fails (leftover POC person)

What to do:

  1. Open the latest poc-run-….log file in Notepad.
  2. Search for MANUAL CLEANUP REQUIRED and copy the exact POC-… id.
  3. Make sure our test program has exited (and is disconnected).
  4. On the tablet alone (or with IAS alone — never both our program and IAS at once), delete only that POC user.
  5. Do not delete real members. Do not reboot as a substitute for deleting the POC user.

Why: The visit is a failure until that temporary id is gone, even if door walks worked.

  • No POC-… user left on the tablet

7. After the visit

  • Save the poc-run-….log file (remove any accidental secrets before sharing).
  • Keep this checklist with notes / tick marks.
  • Do not upload face photos or passwords to git or chat.
  • You may start IAS again only after the test program has fully exited.
What the results mean for the product
  • If laptop face upload still fails with 0x10030110 → keep “enroll face on the tablet” as the product method.
  • If disable/enable and door walks worked → controlling members from our gateway software is justified.
  • If login failed while IAS was open → the rollout checklist must say: stop IAS before starting the gateway service.

8. One-page reminder

  1. Close IAS → backup users → same Wi‑Fi as tablet → start program with IP + admin password.
  2. Watch create of POC-… only → enroll face on tablet for that id → allow walk → disable → deny walk → enable → allow walk → delete.
  3. End only when lists match and log says POC PASS (or you manually deleted any leftover POC id).
